## 先に確かめること

### R1:追跡が切れる条件の再現(#74)

#74 の対応は、担当がターンを終えると背景の Bash の追跡が切れる、という観察に立っている。
一方で、2026-09-11 の別のリポジトリ(非公開)での記録(#31 の表)では、担当は Codex の終了の後に再開し、最終報告を返している。
何が再開を起こしたかは確かめていない。
どちらの挙動になるかを分ける条件が分からないまま定義を変えると、再開する環境で要らない制約を足すことになりうる。

そこで、まず、開発者の手元に退避した 2026-09-11 の証跡(`subagent-299a-transcript.jsonl`)で、再開の直前に何が起きたか(背景のループの完了か、メインセッションからのメッセージか)を確かめる。
そのうえで、偽の `codex` で次の 3 通りを試す。

- 担当が完了の通知だけを待ってターンを終える(現行の定義どおり)。
- 担当が Monitor で `result=` の行を待つ監視を置いてからターンを終える(#74 で起きた形)。
- 担当が背景の Bash に待ちループを置いてからターンを終える(2026-09-11 の形)。この条件の試験に限り、試験用の定義で待ちループの禁止を外す。

どれでも、担当が再開するか、Bash ツールの出力ファイルの末尾が `[killed]` になるか、ラッパーと偽の `codex` が最後まで動くかを記録する。
あわせて、PR-G1 の前提として次の 2 点も確かめる。

- 出力の無いまま 570 秒ほど前面で動く Bash の呼び出し(`timeout` に 600000 を指定)が、途中で打ち切られないか。
- ラッパーの内部で使う `sleep` が、Bash ツールの前面の `sleep` の検査に掛からないか。検査はコマンド文字列に対して行われるので掛からない見込みだが、確かめる。

試験の置き方は次のとおりにする。

- 偽の `codex` は、10 分を超えて眠ってから最終報告と終了コード 0 を返す。利用枠は消費しない。
- ラッパーは `codex` を PATH から探し、定義の `codex_home` は `CODEX_HOME` として渡すだけである。そのため、偽の `codex` への差し替えは PATH で行う。試験用の worktree に別名の GPT 側定義(認証情報の無い一時ディレクトリを `codex_home` にする)と別名の Claude 側定義を置き、Claude 側定義では、偽の `codex` の置き場を PATH の先頭に足してからラッパーを呼ぶ。ラッパーはカレントディレクトリの定義を優先して読む。
- この呼び出しは `bash ~/.claude/tools/codex-agent.sh` で始まらないので、権限の許可規則に当たらない。試験用の worktree の設定で、試験の間だけこのコマンドを許可する。
- 1 条件あたり 15 分以上かかる。3 条件は別の worktree で並行してよい。

結果は #74 にコメントで残す。

#### R1 の結果

追跡が切れるかどうかは、担当の待ち方ではなく、メインセッションが担当を前面(`run_in_background: false`)で起動したかで分かれた。
背景で起動した担当は、通知だけ、Monitor、背景の待ちループのどの形でも、Codex の完了で再開して 2 回目の報告を返した。
前面で起動した担当は、ターンを終えた時点で背景の Bash と Monitor の出力が `[killed]` で終わり、Codex が完了しても再開しなかった。
ラッパーと Codex は `[killed]` の後も最後まで動き、出力ファイルに `result=` の行を書いた。
#74 のメインセッションも担当を前面で起動していた。2026-09-11 の担当の再開は、背景の Bash の完了通知(Codex の終了の 20 秒後)によるものだった。
出力の無い 570 秒の前面の Bash と、内部で `sleep` を使うスクリプトの前面の実行は、どちらも打ち切られなかった。
詳細は [#74 のコメント](https://github.com/ktysne/claude-codex-bridge/issues/74#issuecomment-5858333352)にある。

## 各 PR の内容

### PR-G1:完了を待つ入口(#74)

ラッパーに、実行 ID を受け取って完了を待つ入口を足す。

```bash
bash ~/.claude/tools/codex-agent.sh --wait <実行 ID>
```

待つ処理をラッパーに置くのは、定義が禁じた `sleep` と `until` のループを使わずに前面で待つためと、権限の許可規則が `bash ~/.claude/tools/codex-agent.sh` の先頭一致で判定されるためである。
メインセッションも同じ入口で、担当が残した実行の結果を取り出せる。

契約は次のとおりにする。
呼び出し側は、どの状態かを標準出力の最後の行で判定する。
終了コードは補助にとどめる。ラッパーは Codex の終了コードをそのまま返すことがあり、`--wait` に割り当てた値と重ならないとは言い切れないためである。

- 実行 ID のログを探し、最後の行が `codex-agent: result=` になるまで待つ。1 回の待ちの上限は、`--wait` 自身の起動時刻から数えて 570 秒とし、Bash ツールの上限(600 秒)の内側に収める。ラッパーの生死の照合(下記)は pwsh の起動に数秒かかるので、待ちの初めに 1 回だけ行い、上限の判定の後には置かない。
- ラッパーは、実行のたびに標準出力に出したものを、ログの置き場の `<実行 ID>.report` にも書く。一時ファイルに書いてから改名する。`--wait` が書きかけの `.report` を読むと、途切れた報告を返すためである。`.report` は 7 日より古いものを消す対象に含める。今は完了後に最終報告を取り出す手段が無い。`.last` を残すだけでは、成功時の最終報告しか取り出せず、失敗時の出力(ログの末尾と根拠の行)を再現できない。
- 完了していれば、`.report` の中身をそのまま出す。最後の行は元の実行と同じ `result=` の行になる。終了コードは、定義にある読み替えの規則(`ok` は 0、`rate-limited` と `unavailable` は 75、`failed exit=<code>` はその値、ただし `failed exit=75` は 1)で `result=` の行から戻す。Codex 自身が返した 75 を 75 のまま返すと、実装担当が GPT 側の使用不能と取り違えて Claude 側で作り直すためである。
- 上限までに完了しなければ、最後の行に `codex-agent: waiting run=<実行 ID>` を出して終える。終了コードは、時間切れの慣例の 124 にする。その前の行に、ログの最後の行を進行の目印として 1 行出す。出力の無い待ちが何度も続くと、担当が止まったと判断して途中の報告でターンを終えやすいためである。
- `result=` の行が無いまま、ラッパーのプロセスが無くなっていれば、結果を書かずに消えたとみなし、その旨の行を最後の行に出して終える。R1 で、追跡が切れてもラッパーは最後まで動くと分かったので、この分岐に入ることは少ない。それでも、担当が `--wait` を際限なく繰り返さないための終端として残す。ラッパー本人かどうかは、`run=` の行の PID と `started=` を使い、[gpt-agents.md](../gpt-agents.md) の止める手順と同じ照合(コマンドラインに `codex-agent.sh` を含み、作成時刻が `started=` の前後 60 秒以内)で確かめる。PID の生死だけで判定しないのは、Windows で PID が再利用されるためである。Codex の生死を見ないのは、Codex が先に落ちても、ラッパーが生きていれば `result=failed` を書くためである。
- ラッパーが無くなったのに、コマンドラインに `<実行 ID>.last` を含むプロセスが残っている場合は、Codex が作業ツリーに書き続けている可能性がある。「消えた」とは別の行を出し、止める手順を案内する。
- 実行 ID のログが見つからなければ、起動前の停止と同じ終了コード 2 で終える。

集計(`tools/agent-log-metrics.js`)は次のように変える。

- `codex-agent.sh --wait` の実行を起動に数えない。起動に数えると、1 件の委譲が待ちの回数だけ起動に見えるためである。「待つための Bash」に含めるか別の欄にするかは、PR-G1 で決めて運用記録の測り方に書く。
- 背景へ移った起動を追跡する手がかりに、`run=` の行の実行 ID を足す。`--wait <実行 ID>` の結果の最後の `result=` の行で、元の起動の結果を確定する。今の手がかりは背景の ID と出力ファイルのパスだけなので、PR-G2 の後に担当が出力ファイルを読まずに `--wait` で完了を知ると、背景へ移った起動がすべて「結果不明」になるためである。

テストは、偽の `codex` で、完了済みの実行(成功、失敗、Codex 自身が 75 で終えた失敗)、待ちの上限、結果を書かずに消えた実行、ラッパーだけが消えて Codex が残る実行、見つからない実行 ID を確かめる。
集計のテストには、`--wait` の実行を起動に数えないことと、`--wait` の結果で背景へ移った起動の結果が確定することを足す。

前面で待つ別の形として、ラッパーが Codex を起動元のコンソールから切り離して起こし、最初の呼び出しも 570 秒で `waiting run=` を返して終える形もある。
この形は、R2 の仮説(ターン終了で起動元のコンソールが失われる)に効くことを動機にしていた。
R2 でこの仮説は支持されず、Git Bash から Windows のコンソールを切り離して起動する方法には確かめていない実装上の危険が残る。
そこで、この形は採らない。PR-G2 の配布の後に 0xC0000142 が再び出たら、採否を決め直す(D6)。

### PR-G2:担当が完了までターンを終えない待ち方(#74、#31)

R1 で、前面で起動された担当がターンを終えると追跡が切れることを確かめた。
担当は自分が前面で起動されたかを知る手段を持たないので、どちらで起動されても効く形として、担当が Codex の完了までターンを終えない待ち方にする。
メインセッション側で担当を背景で起動する規則も足すが、補助にとどめる。規則はメインセッションが守らなければ効かず、`Agent` ツールの説明は「次の操作が結果に依存するなら前面で起動する」と勧めているので、規則と食い違いやすい。

- 5 定義の「実行が長引いたとき」:Bash ツールがラッパーを背景へ移したら、`--wait` を前面で繰り返し、`result=` の行が出るまでターンを終えない。`--wait` の呼び出しにも `timeout` に 600000 を指定する。指定しないと既定の 120 秒で背景へ移るためである。完了の通知を待ってターンを終える流れは外す。定義には「ターンを終えてよいのは `result=` の行を読んだときだけ」と書く。
- ターンを終えざるを得ない場合(中断の指示を受けたときなど)の「進行中」の報告は残す。ただし、呼び出し側への案内から「通常は自動で再開する」を外し、`--wait` で結果を取り出す手順に置き換える。出力ファイルの末尾の `[killed]` は Bash の追跡が切れた印であって、Codex の終了ではないことも書く。
- `CLAUDE.md` と `AGENTS.md` の「委譲の検証」と、サブエージェントの待ち方の規則を、同じ内容に直す。あわせて、実装担当を背景で起動する補助の規則を足す。
- [gpt-agents.md](../gpt-agents.md) の既知の制約に、R1 で確かめた条件を書く。
- 前面で起動した担当が、570 秒の待ちを 3 回繰り返して、32 分間ターンを終えずに待ち続けられることは、偽の `codex` で確かめた。
- #31 の残りの effort の比較は、運用記録の「次に測るときに見る点」に既にある。PR-G2 で #31 を閉じ、M2 で比べる(D8)。

グローバルの `~/.claude/CLAUDE.md` にも「サブエージェントは、待っていた処理が終わると通常は自動で再開し」の記述がある。
リポジトリの外のファイルなので、PR-G2 のマージの後、ユーザ側への配布と同時に、開発者の確認を取って直す。背景で起動する補助の規則も、同じ機会に足す。
配布はラッパー、定義、グローバルの `CLAUDE.md` の順に行い、配った時刻を運用記録に残す。
次の測定は、この時刻から始める。

### PR-H:子プロセスの起動失敗と検証の代行(#53、#75)

#53 の `spawn EPERM` と #75 の 0xC0000142 は、原因は別でも、Codex が依頼文の検証を実行できないまま報告を返す点が同じである。
そこで、両方を 1 つの仕組みで報告に出す。
主な対象は #53 である。R3 で、`spawn EPERM` はサンドボックスの構造による失敗で、Codex 側では避けられないと分かった。
#75 は R2 で、追跡が切れた後にだけ出ていたと分かった。PR-G2 でその経路は塞がる見込みなので、PR-H では再発を観測するための印として数えるだけにする。

- ラッパーは、実行の標準エラーに子プロセスの起動失敗の印が出た回数を数え、1 件以上なら `codex-agent: warning=child-spawn-failed count=<回数>` の行と、最初の根拠の行を出す。`result=` の値は変えない。`ok` を 75 に変えると、GPT 側の実装を捨てて Claude 側で作り直すことになるためである。
- 警告の行は、最終報告の前(`log=` の行と `warning=concurrent-writer` の行の後)に出す。`result=` の行の直前には、終了コード 75 の根拠の行が来ると定義が決めているためである。
- 印の照合は、0xC0000142 については Codex がツールの完了を書く形(`exited -1073741502 in`)に限る。ログには Codex が読んだファイルの中身も流れるので、数値だけで照合すると、この計画や Issue を読んだだけで一致する。`spawn EPERM` は語のまま照合し、誤って一致した場合は Claude 側で検証を再実行するだけで済むことを許容する。
- `impl-hard`、`impl-light`、`impl-standard` は、終了コード 0 でこの警告の行があるか、最終報告が依頼文の検証を実行できなかったと述べている場合に、Claude 側で依頼文の検証コマンドだけを実行し、結果を報告に添える。コードは変えない。検証が失敗しても直さず、失敗の出力を添えて報告する(D7)。定義の「Claude 側の進め方」にある「失敗した場合は原因を調べて直す」は、この経路には当てはめないことを明記する。報告では、検証を Claude 側で実行したことを明示させる。
- `codex-review` と `codex-subagent` は、警告の行を報告の冒頭にそのまま添えるだけにする。どちらも Codex の結果をそのまま返す役割であり、`codex-review` は読み取り専用でもあるためである。
- [gpt-agents.md](../gpt-agents.md) の既知の制約に、`spawn EPERM` と、R3 で調べた設定の有無を書く。

GPT 側の定義に「子プロセスを起こす検証は `EPERM` になるので、試さずに未実施と書く」と足せば、Codex が失敗する検証を繰り返す往復を減らせる。
ただし、`elevated` で `EPERM` が消えるなら、この文言は環境によって誤りになる。D9 の結果が出てから入れるかを決め、PR-H はこれを待たずに進める。
