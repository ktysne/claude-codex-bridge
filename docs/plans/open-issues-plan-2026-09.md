## 実施の単位と順序

### 挙動を変える PR のマージを再測定の後に回す理由

2026-09-23 に、PR #36 の効果を見るため、1 週間分の運用を測り直す。
測る期間の途中でサブエージェントの挙動を変えると、新旧の挙動が同じ期間に混ざり、PR #36 の効果と区別できなくなる。
そこで、PR を次の 2 種類に分けて扱う。

- **挙動を変えない PR**：テスト、集計スクリプト、cross-review の通知文言を変えるもの。再測定の前にマージしてよい。
- **挙動を変える PR**：ラッパー、Claude 側の定義、CLAUDE.md の設計原則を変えるもの。実装とレビューは先に進め、マージとユーザ側への配布を再測定の後に行う。リポジトリ側の定義と CLAUDE.md は、このリポジトリで動くセッションにはマージした時点で効くため、配布だけを遅らせても期間の混在は防げない。

### 順序と依存関係

```
再測定（2026-09-23）の前にマージする
  PR-A1  codex-agent.sh のテスト（#38）
  PR-A2  agent-log-metrics.js のテスト（#38）
  PR-F   委譲の結果を理由別に数える（#34 の判断材料）   PR-A2 の後
  PR-B   上流 ai-cross-review#49 の修正 → PR-C 同期（#37）
再測定の前に実装とレビューを進め、後でマージする
  PR-D   実行中の観測（#31）                            PR-A1 の後
再測定の後
  PR-D のマージとユーザ側への配布
  PR-E1  実装担当に許す操作（#34） → PR-E2 worktree の書き込み担当（#35）
  雑務を実装担当へ回さない運用を続けて測り、impl-light の役割を決める（#34）
```

依存関係の理由は次のとおりである。

- PR-F を PR-A2 の後にするのは、集計を変える前に、今の数え方をテストで固定するためである。
- PR-D を PR-A1 の後にするのは、ラッパーの分岐をテストで固定してから、出力と中断の扱いを変えるためである。PR-D のテストは PR-A1 の仕組みに足す。
- PR-E2 を PR-D の後にするのは、同じ worktree での重複起動の検出に、PR-D で足す実行 ID を使うためである。
- PR-E1 と PR-E2 は、CLAUDE.md の同じ設計原則の節と、定義の禁止事項を変える。PR-E1 を先に入れ、PR-E2 をその上に積む。

PR-A2 のテストで集計の誤りが見つかり、それを直して数え方が変わった場合は、直したスクリプトで 2026-09-09 から 2026-09-16 を数え直し、運用記録に併記する。
運用記録は、古い値を書き換えない規則で残しているためである。

### 作業の分担

- `CLAUDE.md` と `AGENTS.md` の変更は、メインセッションが行う。実装担当の定義（impl-*）が、この 2 ファイルの変更を禁じているためである。
- `tools/codex-agent.sh` の変更は Claude 側で行う。Codex に書き換えさせると、実行中の bash が書き換え後の内容を読んで壊れることがある（[gpt-agents.md](../gpt-agents.md) の既知の制約）。
- 並行して進める PR は、それぞれ別の worktree で作業する。1 つの worktree に同時に書き込む担当を 1 つに保つためである。

## 各 PR の内容

### PR-A1：codex-agent.sh のテスト（#38）

偽の `codex` を PATH の先頭に置き、実モデルと実認証情報を使わずにラッパーの分岐を通す。
テストは `tools/test/codex-agent.test.sh` の 1 本にし、Git Bash から `npm run test:codex-agent` で起動する。

偽の `codex` を置くだけでは、環境の分離が足りない。
ラッパーは定義をカレントディレクトリと利用者ホームから探し、ログを利用者ホームの下に作って古いログを削除するため、実際の設定とログに触れうる。
そこで、環境を次のように分ける。

- ケースごとに一時ディレクトリを作り、USERPROFILE と HOME を同じ一時パスに向ける。ラッパーは USERPROFILE を優先して読む。
- 一時のカレントディレクトリに定義を置き、認証情報の無い一時ディレクトリを codex_home にする。
- PATH を一時の bin と `/usr/bin` だけにし、偽の `codex` が実際に呼ばれたことをケースごとに確かめる。
- 定義にはテスト専用のエージェント名を使い、実ホームのログ置き場にその名前のログが現れないことを確かめる。実ホームのログ一覧を前後で比べないのは、並行して動く実際の委譲がログを足したり消したりするためである。

固定するケースは次のとおりである。

- **認証ホーム**：`exec --help` と `exec` の両方に、定義で選んだ CODEX_HOME が渡る。
- **起動引数**：sandbox、`-m`、effort（`--effort` による上書きと既定値）、`-C` が定義どおりに渡り、`approval_policy=never` がちょうど 1 回渡る。
- **出力の構成**：成功時に、監査行、`log=` の行、最終報告、`result=ok` の行がこの順で出て、経過はログにだけ残る。`--output-last-message` が無い版と、最終報告のファイルが空の場合は、標準出力の末尾で代える。最終報告が改行で終わらなくても、result 行が独立した行になる。
- **失敗の分類**：利用上限、モデルの混雑、通常の失敗が、それぞれ `rate-limited`、`unavailable`、`failed exit=<code>` になる。根拠の行は 1 行ずつ接頭辞付きで result 行の直前に並ぶ。Codex 自身の 75 は 1 になる。成功した本文に上限の語があっても成功のままで、ログの中ほどにだけある語では分類しない。`429` は単語として照合する。
- **起動前の停止**：終了コード 2 と 3 の理由ごとに、理由の行が出て、Codex を起動しない。
- **定義の探索**：カレントディレクトリの定義がホームの定義より優先し、フロントマターの行末コメントと引用符を除く。
- **ログ**：同時に起動してもログ名が衝突しない。WARNING 行と hook 行をログから除く。9 日前のログを消し、6 日前のログを残す。POSIX の権限が効く環境でだけ権限を検査し、効かない環境では検査を飛ばしたことを出力に明示する。
- **試験用フック**：`CODEX_AGENT_SIMULATE_RATE_LIMIT` と `CODEX_AGENT_SIMULATE_UNAVAILABLE` が、Codex を起動せずに終了コード 75 を返す。
- **ai-cross-review との契約**：`tools/cross-review.js` の `scriptPinsApprovalNever` が、実際の `tools/codex-agent.sh` に対して真を返す。ai-cross-review は、この判定が真のときに限って bridge 経由の起動を選ぶ。

テストで見つかったラッパーの欠陥は、期待する仕様でテストを書いたうえで、Claude 側が直す。

### PR-A2：agent-log-metrics.js のテスト（#38）

`node:test` と固定した入力で、スクリプト冒頭のコメントと運用記録に書いた数え方の約束を固定する。
入力の JSONL と meta.json は、テストの中で一時ディレクトリへ書き出す。
`npm run test:metrics` で起動する。

固定する約束は次のとおりである。

- ヒアドキュメントと引用の中のコマンドを、実行したものと数えない。
- 同じ分に起動した別々の実行を、別々に数える。
- 同じ依頼文や、共通の接頭辞を持つ依頼文の委譲を、meta.json の toolUseId で正しい実行に紐付ける。
- meta.json が無い委譲を「紐付け不明」に数え、Codex 未呼出に加えない。
- 期間の境界を数値で比べ、子の実行が日付をまたいでも紐付ける。
- 読めない入力と解析できない行を、件数として報告する。

約束に反する挙動が見つかった場合は、テストを todo として残し、修正は別に行う。

### PR-F：委譲の結果を理由別に数える（#34 の判断材料）

今の集計は、委譲ごとに「Codex を起動したか」だけを見ている。
#34 で impl-light の役割を決めるには、Codex へ渡らなかった理由を分けて見る必要がある。
そこで委譲ごとの結果を、GPT 側で実行した、未設定で Claude 側へ倒れた（終了コード 3）、GPT 側が使えず倒れた（終了コード 75）、権限判定で拒否された、起動しなかった、に分ける。
起動しなかったもののうち、委譲を止める明示の指定があるものは分けて数える。
指定の書き方は PR-E1 で決めるので、それまでは明示の指定を見分けられない。
PR コメントの投稿やブランチの載せ替えといった実装でない作業は、記録から機械的に見分けにくいので、運用記録で件数を確かめる。

### PR-B と PR-C：終了コード 75 の原因の区別（#37）

`tools/cross-review.js` は上流の ai-cross-review から取り込んでいるため、上流の [#49](https://github.com/ktysne/ai-cross-review/issues/49) で直し、このリポジトリで `npm run sync:cross-review` を実行して取り込む。
取り込み先で直接編集すると、次の同期で失われるためである。
同期では、同じ時期に上流へ入った [ai-cross-review#51](https://github.com/ktysne/ai-cross-review/pull/51)（指摘に推奨の対応方法を添えさせる変更）も一緒に取り込まれる。

上流では次のように直す。

- 終了を分類する関数を足し、フォールバックするかどうかと、原因（`rate-limited`、`unavailable`、`unknown`）を分けて返す。
- bridge 経由で 75 のときは、出力の末尾で行頭が `codex-agent: result=` の行のうち、最後の 1 行から原因を読む。Codex の最終報告が result 行を引用していても誤判定しないためである。
- result 行が無いか値が未知なら、フォールバックはしたうえで、通知を「理由不明の GPT 側使用不能」にする。原因を読めないときに利用上限と断定すると、記録が事実と食い違うためである。
- 75 以外の終了を、出力の文字列だけでフォールバックに変えない。直接起動の判定、`--no-fallback`、終了コード、往復を数えない扱いは変えない。
- 端末の通知、PR コメントの案内、docs、SKILL の記述を原因ごとに分ける。

### PR-D：実行中の観測（#31）

評価コメントの訂正を踏まえ、#31 の残件を、実行中の観測と、進行中と完了の区別に絞る。
ラッパーを次のように変える。

- Codex を起動する前に、`codex-agent: run=<実行 ID> pid=<ラッパーの PID> started=<開始時刻>` の行と `codex-agent: log=<パス>` の行を出す。今は Codex の終了後に `log=` の行を出しているため、実行中はログの場所が分からない。
- Codex の標準エラーを、実行中からログへ追記する。WARNING 行と hook 行は、ログへ書く時点で除く。ログの 1 行目に `run=` の行、最後の行に `result=` の行を書き、ログだけで完了を判定できるようにする。
- 終了コード、result 行、`approval_policy=never` を `codex exec` と同じ論理行に書く形は変えない。
- `--json` のイベント出力は採らない。実行中の観測に要るのは経過がログへ追記されることであり、標準エラーの経過をそのまま追記すれば足りるためである。

中断の扱いは、Windows と Git Bash で調べた次の結果で決めた。

- Claude Code の Bash ツールでバックグラウンドのコマンドを止めると、止まるのはツールが起動した最上位のシェルだけで、ラッパーと Codex は残る。シグナルは届かず、trap も動かない。
- ラッパーの PID を `taskkill /T` に渡しても、Codex までは止まらない。npm のシム(`sh`)を経由すると、Windows 上の親子関係がラッパーから途切れるためである。

そのため、ラッパーには停止の処理を持たせない。
止める手順(ラッパーの PID、コマンドラインに `<実行 ID>.last` を含むプロセスの順に `taskkill /T /F` で止める)を `docs/gpt-agents.md` に書く。

Claude 側の 5 定義は、「実行が長引いたとき」と「出力の読み方」の節を直す。
result 行を確認できないままターンを終えるときは、報告の冒頭に「進行中」と書き、`run=` の行と `log=` の行を添える。
CLAUDE.md と AGENTS.md の「委譲の検証」には、「進行中」の報告を、完了の報告としても委譲をやり直す理由としても扱わないことを足す。result 行を含まない報告を無効としてやり直すと、残った Codex と重なるためである。
配布の途中で古いラッパーが残っていても動くよう、`run=` の行が無い場合も読める書き方にする。
配布はラッパー、定義の順に行い、配布した時刻を運用記録に残す。

effort は変えない。
再測定で、実行時間とトークン量を比べてから決める。

テストは、偽の `codex` で、実行中の出力とログ、完了後のログの最後の行、止める手順を確かめる。

### PR-E1：実装担当に許す操作（#34）

決めることは、下の「開発者の判断が必要な事項」の D3 と D4 である。
決めた内容を、Claude 側と GPT 側の定義、docs、CLAUDE.md と AGENTS.md に揃えて書く。

- 通常の依頼、Claude 側での実装の指定、コミットの要求、push の要求、禁止操作の要求の 5 つの例について、担当と許す操作が一意に決まる表を定義に書く。
- コミットをメインセッションに集約する場合は、メインセッションが行う監査の最低限（差分を読む、検証コマンドを再実行する）も書く。
- PR コメントの投稿やブランチの操作を、実装担当へ回さない運用を CLAUDE.md に書く。
- ユーザ側の GPT 側定義は丸ごと配らない運用なので、役割文の変更は本文だけを反映する。

impl-light の役割は、雑務を回さない運用を始めてからの期間を PR-F の集計で測り、その結果で決める。

### PR-E2：worktree の書き込み担当（#35）

決めることは、下の「開発者の判断が必要な事項」の D1 と D2 である。

- CLAUDE.md、AGENTS.md、定義、docs の「作業ツリーの分離」を、「1 つの worktree に同時に書き込む担当は 1 つ」という不変条件で書き直す。`review:codex --fix` も書き込む担当に含める。
- `codex-subagent` の定義から、別 worktree の指定を必須とする記述を外す。カレントディレクトリが対象の worktree なら、`-C` を省いてよい。
- ラッパーは、書き込み可能な起動のときに、worktree 固有の git ディレクトリへ実行の目印（実行 ID、PID、開始時刻）を置く。同じ worktree に動いている目印があれば、警告の行を出す。
- 警告の根拠に、`-C` とカレントディレクトリのパス比較を使わない。すでに分離した worktree の中から起動した正当な呼び出しと区別できないためである。
- 親セッションの worktree ルートを記録する受け渡しは設けない。メインセッションの編集はラッパーから観測できず、記録しても検出できる範囲が変わらないためである。
- 警告から排他へ上げる条件（再測定で並行が残っており、かつ古い目印を Windows で正しく見分けられると確かめた場合）を PR に書く。
- Agent ツールの `isolation: "worktree"` を並行の手段として採るかどうかと、その理由を書く。
- テストは、同じ worktree での二重起動、別 worktree での並行、中断後の再実行を、偽の `codex` で確かめる。

## 開発者の判断が必要な事項

| 番号 | 論点 | 推奨 | 推奨の理由 |
|---|---|---|---|
| D1 | 同じ worktree での並行（#35） | 1 つの worktree に書き込む担当は同時に 1 つとする。並行させたいときは担当ごとに別 worktree を使う。`codex-subagent` も同じ worktree を使ってよいが、そのあいだメインセッションはその worktree を編集しない | 担当するファイルを分けても、ビルドの生成物、テストの実行、git の索引は共有されるため |
| D2 | 違反の検出（#35） | 警告の行だけを出す観測の補助から始め、再測定で並行が残っていれば排他へ上げる | Windows で古い目印を正しく見分けられるかを確かめていない。誤って止めると、その worktree の委譲がすべて止まる |
| D3 | コミット、push、PR への投稿（#34） | 実装担当は作業ツリーの変更までとし、コミット以降はメインセッションが差分を監査したうえで行う | 監査の役割と合い、メインセッションと実装担当のコミットが衝突しない。メインセッションが書いた依頼文だけで実装担当の権限が増える構成を避けられる |
| D4 | 委譲を止める指定（#34） | 依頼文に `委譲: Claude 側で実装` の 1 行を置く形に統一し、指定を適用した理由と実行経路の報告を必須にする | 書き方がそろえば、サブエージェントが定義と依頼文のどちらに従うかを裁定しなくて済む |

## 未解決の点

- effort の比較に使う検証の合格率と手戻りは、今の集計では取れない。再測定では実行時間とトークン量で比べ、この 2 つは未解決として運用記録に残す。
- `--output-last-message` を持たない版の Codex では `-o` を渡さないため、止める手順の `<実行 ID>.last` で Codex 側のプロセスを探せない。
- #15 の close は、実施前に開発者の確認を取る。
