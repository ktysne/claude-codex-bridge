# GPT 系サブエージェントの運用記録(2026-09-16)

## この文書の役割

Claude Code のセッション記録から、GPT 系サブエージェントの運用を測った結果と、そこから直した内容を残す。
次に測るときの基準値として使う。
数え方をここに固定してあるので、同じ規則で数え直せば前回との差が読める。

## 測り方

記録の置き場は `%USERPROFILE%\.claude\projects` である。
この下にセッションごとの `.jsonl` があり、サブエージェントの記録は `<セッション>/subagents/` に入る。
1 行が 1 件の出来事で、`message.content` の中に `tool_use` と `tool_result` が並ぶ。

期間は、日付か、タイムゾーン付きの日時で指定する。
日付は UTC の日として解釈し、開始日の `00:00:00.000` から終了日の最後のミリ秒までを含む。
日時は開始の時刻を含み、終了の時刻を含まない。
配布の時刻を境に前後を数えたとき、境界の記録を二重に数えないためである。
時刻の比較は数値で行う。
文字列で比べると、ミリ秒を持つ時刻(`...T00:00:00.000Z`)が `...T00:00:00Z` より小さくなり、開始日の先頭が落ちる。
日時が読めない記録は、実績 0 に混ぜず件数を出す。

測る指標は 4 つである。

- **実起動**：`codex-agent.sh` を起動した Bash の呼び出しのうち、結果が記録に残ったものの件数。`codex-agent: result=` の値(`ok`、`rate-limited`、`unavailable`、`failed exit=<code>`)で分ける。結果がその場で分からない起動と、疑似の起動は含めない。
- **バックグラウンドへの移行**：結果の本文に「moved to the background」が出た起動の件数。Codex の実行時間が Bash の上限を超えた回数を表す。
- **出力の退避**：結果の本文に「Output too large」が出た件数と、その最大のサイズ。
- **待つためだけの Bash**：Codex を呼んだサブエージェントの中で、バックグラウンドの出力ファイル(`.../tasks/<ID>.output`)を読むか、`sleep` か `until` をコマンドとして実行する Bash の呼び出しの件数。Codex の起動そのものは含めない。

あわせて、実起動から除いた起動の件数を 2 つ出す。

- **最初からバックグラウンドで起動した起動**：Bash の `run_in_background` で起動し、結果の本文が「Command running in background with ID:」で始まる起動の件数。上限を超えて移った起動とは分ける。こちらは実行時間ではなく、起動した側の選択を表すためである。
- **疑似の起動**：ラッパーの試験用フックが、Codex を起動せずに出した結果で終わる起動の件数。フックは `result=` の値の後ろに ` (simulated)` を付ける。

あわせて、定義ごとの内訳(親から見た委譲、Codex を呼ばなかった件数、`git commit` を実行した件数、サブエージェントを起動した件数、紐付け不明の件数)を出す。

定義ごとの**委譲の結果**も出す。
紐付けできた委譲 1 件を、次の 7 つのうちちょうど 1 つに数える。

- **GPT で実行**：最後の起動の結果が `ok`。
- **未設定**：最後の起動の結果が `failed exit=3`。GPT 側が未導入、無効化、未設定で、Claude 側へ倒れた。
- **GPT 使用不能**：最後の起動の結果が `rate-limited` か `unavailable`。
- **GPT で失敗**：最後の起動の結果が、それ以外の `failed exit=<code>`。
- **拒否**：最後の起動が、権限判定などで実行されなかった。
- **結果不明**：最後の起動の結果が記録から読めない。
- **未起動**：子が `codex-agent.sh` を一度も起動していない。件数は Codex 未呼出と一致する。

あわせて、定義ごとに**委譲を止める指定**がある委譲の件数と、そのうち子が `codex-agent.sh` を起動しなかった件数を出す。
委譲を止める指定とは、GPT 側へ委譲せず Claude 側で実装させるために、依頼文の最初の空でない行に置く `委譲: Claude 側で実装` の行である。
未起動のうち指定によるものを分けて見ると、指定の無い未起動(実装でない作業の流入や、指定を使わずに委譲を止めた依頼)を読み取れる。
この指定を認識して委譲を止める規則は、PR #50 で `impl-hard`、`impl-light`、`impl-standard` の定義に入る。
#50 がマージされてユーザ側へ配られるまでは、定義が指定を認識しないため、指定の件数は 0 になるか、指定があっても GPT 側で実行された委譲として現れる。
配る前の期間の値は、指定の効き目を表さない。

数え方の約束は次のとおりである。

- 起動は Bash の呼び出し 1 件を 1 件と数え、tool_use の識別子でまとめる。会話を引き継いだセッションは、前のセッションの記録を識別子ごと写すためである。待つための Bash と委譲も、同じく識別子でまとめる。時刻ではまとめない。まとめると、同じ分に並行して起動した別々の実行が失われる。
- セッションが作業ディレクトリを移ると、同じセッションの記録が別のプロジェクト置き場にも書かれる。置き場より後ろの相対パスが同じ記録は、最も大きい記録の先頭と全バイトが一致するものを複製として除く。一致しないものは除かずに数え、「前方一致しない複製」として件数を出す。前提が崩れたときに、値を黙って変えないためである。除いた複製の脇にだけ `.meta.json` がある場合は、それを紐付けに使う。
- 依頼文はヒアドキュメントでコマンドに埋め込まれるため、照合の前にその本文を落とす。落とさないと、依頼文が話題にしている語(`git commit` など)を実行したものとして数える。
- 起動の判定は、コマンドを実行単位へ切り出してから行う。区切りは `;`、`&`、`|`、改行である。引用符の中とコメントの中にある区切りは区切りとして扱わない。改行だけで切ると、複数行の引用文字列に書いた例を実行と取り違える。
- `cat tools/codex-agent.sh` のようにスクリプトを読むだけのコマンドは起動と数えない。`bash` または `sh` がスクリプトを実行している形だけを数える。先頭に並ぶ環境変数の代入は読み飛ばす。
- `bash -n` による構文検査と、`-h` か `--help` を渡した用法の表示は、起動と数えない。どちらも Codex を起動しないためである。
- result 行は、行頭から行末までが `codex-agent: result=<値>` の形の行で、本文の最後のものを使う。Codex の最終報告が result 行を引用することがあり、ラッパーは自分の result 行を出力の最後に出すためである。行頭に付いた `grep -n` の行番号は読み飛ばす。
- 実起動の内訳で、出力が退避された本文は「結果行なし」に数える。退避された本文は冒頭の抜粋で、最終報告が引用した result 行が入りうるためである。
- 委譲 1 件は Agent の呼び出し 1 件である。同じ依頼文を出し直した場合も、それぞれ別の実行を伴うので別の委譲として数える。
- サブエージェント起動は、子の記録にある Agent ツールの呼び出しで数える。
  孫の記録は親の tool_use と紐付かないため、孫が Codex を起動しても親から見た委譲は Codex 未呼出のままになる。
- 委譲と実行の紐付けは、サブエージェントの記録の脇にある `<名前>.meta.json` が持つ親の tool_use の識別子で行う。依頼文の一致で推測すると、同じ依頼文を出した別の定義や別の時期の実行と取り違える。
- 委譲の期間は親の起動時刻で選ぶ。子の実行が日付をまたぐことがあるため、子の側では期間で絞らない。
- 対応する実行を特定できない委譲は「紐付け不明」として数え、未呼出には加えない。別の実行の状態を流用しないためである。
- 委譲の結果は、子が `codex-agent.sh` を起動した Bash の呼び出しのうち、最後のものの結果で分類する。子は失敗や上限のあとに起動し直すことがあり、委譲の行き先を決めたのは最後の起動だからである。疑似の起動は起動として扱わない。子の起動がすべて疑似なら、その委譲は未起動である。
- 拒否は、ツール結果にエラーの印が付き、本文が `Exit code` で始まらず、`codex-agent:` の行も含まないもので見分ける。拒否の文言は、自動モードの分類器、ユーザ、worktree の隔離など、拒否した仕組みごとに違うためである。
- 起動がバックグラウンドへ移った場合と、出力が退避された場合は、その後に子がバックグラウンドの ID や出力ファイルのパスを指定して読んだ結果から、result 行を拾う。手がかりで結び付かない読み取りの result 行は使わない。差分や文書を読んだ結果にも result 行が現れるためである。
- 委譲を止める指定は、依頼文の最初の空でない行だけで判定し、前後の空白を除いて完全に一致するものだけを数える。2 行目以降やコードブロックの中にある同じ文字列は数えない。定義や文書にはこの行そのものが書かれており、それらを引用した依頼を指定と取り違えないためである。紐付け不明の委譲も指定の件数には数えるが、Codex を起動したかは分からないので、未起動の件数には数えない。

読めなかった場所と、解析できなかった行は、件数を出す。
測れなかったことと、実績が無いことを取り違えないためである。

数え方の約束を変えたときは、集計スクリプトが出す「数え方の版」を上げる。
この節は版 2 の約束である。
「2026-09-16 時点の値」は版 1 で数えた。
版 1 は、構文検査と用法の表示を起動と数え、最初からバックグラウンドで起動した起動と疑似の起動を実起動に含め、複製された記録と写された呼び出しを二重に数えていた。

出た値はすべて下限である。
理由は 2 つある。
Codex の実行はバックグラウンドへ移ることがあり、その出力が記録に残らない場合がある。
もう 1 つは、分類を終了コードと `result=` の行だけで行っている点である。
`codex exec` は依頼を果たせなくても自分の応答を返せば 0 で終わるため、「終了コード 0 だが報告はできなかった」という失敗はこの集計に現れない。

逆に、実起動が多めに出る場合もある。
開発中の試験で偽の `codex` を PATH に置いて起動したものは、本物の起動と見分けられず実起動に入る。

### 判断

下がるはずだった指標は、配布後にどれも下がった。

- `sleep` と `until` で待つ実行は、72 件から 0 件になった。配布前は起動 1 件あたり約 0.6 件(起動 122 件で 72 件)出ていたので、挙動が変わっていなければ、配布後の起動 18 件で 10 件前後出るはずである。0 件は偶然では説明しにくい。
- 出力の退避は、16 件から 0 件になった。ただし、配布前の割合(起動 122 件で 16 件)のままでも、起動 18 件で 0 件になる確率は約 8% ある。件数が少なく、偶然の可能性は残る。
- 実起動の「結果行なし」2 件は、どちらも出力を読めなかった起動ではない(拒否と、起動前の構文エラー)。
- 委譲の結果不明は、配布前の 12 件から 0 件になった。

判定の語が足りているか(`failed exit=1` が `unavailable` へ移るか)は、まだ判断できない。
配布後に、モデルの混雑が起きていないためである。
配布前の `failed exit=1` の 1 件は存在しないモデル名を指定した試験で、版 1 で `unavailable` に数えた 1 件は試験用フックの疑似の結果だった。
版 1 の値にも、判定の語の過不足を読める材料は無い。

`impl-light` の役割(#34)も、まだ判断できない。
配布後の `impl-light` への委譲は 1 件だけである。

バックグラウンドへの移行は、見込みどおり残った。
配布後に移った 8 件は、Codex の実行が Bash の上限(10 分)を超えたことで説明できる。
実行ログでは、`impl-standard` の 11 件のうち 7 件と `impl-hard` の 1 件が 10 分を超えており、合わせて 8 件になる。
減らす手は effort の見直しで、#31 に残っている。

最初からバックグラウンドで起動した起動は、25 件から 0 件になった。
原因は切り分けていない。

## 次に測るときに見る点

対応が効いていれば、次の 3 つが下がる。

- **待つためだけの Bash。** 定義は `sleep` と `until` のループを禁じ、プロセスの一覧や出力ファイルの探索も禁じている。出力ファイルを読むこと自体は回数を制限していないので、この指標が 0 になるとは限らない。見るのは、`sleep` と `until` が消えたかどうかと、1 件の起動あたりの回数が数回に収まっているかである。減らないなら、定義がユーザ側へ配られていないか、セッションを再起動していない。
- **出力の退避と「結果行なし」。** 標準出力を絞ったので、どちらもほぼ 0 になるはずである。残るなら、依頼文が大きいか、ユーザ側のスクリプトが古い。
- **`failed exit=1`。** モデルの混雑がここに落ちなくなり、`unavailable` へ移るはずである。`unavailable` が現れず `failed exit=1` が残るなら、判定の語が足りていない。ログの `ERROR` 行を読んで語を足す。

下がらない指標も見る。

- **バックグラウンドへの移行。** これは Codex の実行時間そのものなので減らない。減らす手は effort を下げることであり、#31 に残っている。
- **委譲の内訳と委譲の結果。** `impl-light` の未呼出が多いままなら、実装でない雑務が流れ込んでいる可能性がある。委譲の結果の表で、未起動、拒否、結果不明を分けて見る。委譲を止める指定の表で、未起動のうち指定によるものを除いて見る。#34 の判断材料になる。
  サブエージェント起動が 0 でなければ、実装担当が Codex を直接呼ばずに孫のサブエージェントへ任せている。
  これは、実装担当の定義が Agent ツールを禁じていない(禁じる設定がユーザ側へ配られていない)兆候である。
- **指定の無い未起動。** 指定の無い未起動が続くときは、その委譲の依頼文を読み、理由を分ける。実装でない作業の流入か、指定を使わずに自由文で委譲を止めた依頼かである。後者は、メインセッションが依頼文で定義の委譲方針を上書きしている兆候なので、件数と依頼文の言い回しを開発者に伝える。集計は指定の形式しか数えないため、自由文の指示は指定の無い未起動としか現れない。

測ったら、この文書の「2026-09-16 時点の値」の下に同じ形で追記する。
古い値を書き換えない。差が読めなくなるためである。
